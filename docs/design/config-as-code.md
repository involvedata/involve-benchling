# Design: Benchling configuration as code

| | |
|---|---|
| Status | Draft, for review |
| Date | 2026-10-20 |
| Module | `involve_benchling.config`, with a `benchling-config` CLI behind the `config` extra |
| Prior art | [Liminal ORM](https://github.com/dynotx/liminal-orm) |

## Summary

A Benchling tenant's configuration (schemas, fields, dropdowns and so on) lives in YAML state
files in a git repository. A CLI built on involve-benchling has three main commands:
- **`export`** reads a tenant into state files.
- **`plan`** compares state files with a live tenant and lists the changes needed.
- **`apply`** makes a reviewed plan's changes through the Benchling V3 API.

The design is declarative, like Terraform. Changes are reviewed as pull requests and promoted
from dev to test to prod.

## Motivation

- Today all configuration changes go through Benchling's native tools: the admin UI and
  configuration migration. Nothing records what a tenant's configuration was, who changed it,
  or why.
- Configuration in git gives:
  - history and blame
  - review before a change lands
  - the same change applied to dev, test and prod
  - detection of changes made by hand
- The V3 API can read all of this configuration and write most of it.

## Goals

- Tenant configuration reviewable and versioned in git.
- Bootstrap any existing tenant with no hand-written files.
- Show drift: anything changed in the tenant that git doesn't know about.
- Apply changes safely, in dependency order, with destructive changes opt-in.
- Promote one change set across environments whose object IDs differ.

## Non-goals

- Moving data (entities, results, entries). This design covers configuration only.
- Replacing Benchling's UI for exploratory configuration in dev.
- Anything the V3 API cannot write (see [API coverage](#api-coverage)). Those changes appear in
  plans as manual steps.

## Architecture

| Layer | Home | Responsibility | Credentials |
|---|---|---|---|
| Mechanics | `involve_benchling.config` | Config model, export, plan, apply | Takes a client from its caller |
| CLI | `benchling-config` entry point (`involve-benchling[config]`) | Commands, plan files, safety checks | Read-only app for export and plan; admin app for apply |
| Config repo | Owned by the user, one per Benchling organization | State files, environment definitions, ID maps, CI | Admin app secrets, in CI only |

```
involve_benchling.config     library: model, export, plan, apply
          ▲
          │
benchling-config CLI         commands, plan files, safety checks
          ▲
          │
config repo                  state files + CI
```

- Export and plan are pure reads, so other read-only tools (audits, documentation generators)
  can call them without the CLI.
- Keeping apply beside them means the model and the API mapping are defined once.
- The `config` extra holds the CLI's dependencies (YAML, a CLI framework), so the core install
  stays small.

### Library module

```
involve_benchling/config/
├── model.py      # Pydantic models for state files (desired configuration)
├── export.py     # live tenant -> model -> YAML
├── plan.py       # desired model vs live tenant -> ordered list of operations
├── apply.py      # execute a plan through the SDK
├── idmap.py      # system name <-> tenant ID, per environment
└── cli.py        # benchling-config entry point
```

- `apply` refuses a read-only client.
- `apply` also requires an explicit `allow_writes=True` and the hash of the plan being applied.

## State files

### Layout of a config repo

```
benchling-config/
├── config/                         # desired configuration (identical across environments)
│   ├── dropdowns/<registry>/<name>.yaml
│   ├── fieldsets/<system_name>.yaml
│   ├── schemas/entity/<system_name>.yaml
│   ├── schemas/result/<system_name>.yaml
│   ├── schemas/entry/<system_name>.yaml
│   ├── schemas/storage/<family>/<system_name>.yaml
│   └── units/<name>.yaml
├── environments/
│   ├── dev.yaml                    # tenant URL, registry keys -> registry names
│   ├── test.yaml
│   └── prod.yaml
├── ids/                            # generated by export, committed, never hand-edited
│   ├── dev.json
│   ├── test.json
│   └── prod.json
├── plans/                          # git-ignored; plan files awaiting apply
└── .github/workflows/              # CI: plan on pull requests, apply on merge and tags
```

### Example

```yaml
# config/schemas/entity/plasmid_lot.yaml
kind: entity_schema
type: custom_entity
system_name: plasmid_lot
name: Plasmid Lot
registry: main                      # key from environments/<env>.yaml
prefix: PLL
naming:
  options: [NEW_IDS]
  template:
    - field: plasmid
    - separator: "-"
    - lot_number_of: plasmid
fields:
  - system_name: plasmid
    name: Plasmid
    type: dna_sequence_link
    target: plasmid                 # schema system name
    required: true
    parent: true
  - system_name: concentration_mg_ml
    name: Concentration (mg/mL)
    type: decimal
    min: 0
  - system_name: vendor
    name: Vendor
    type: dropdown
    dropdown: main/Vendor           # dropdowns have no system name; registry key + name
fieldsets: [orderable_material]
validation_rules: []
```

### Identity

| Object | Key in state files | Notes |
|---|---|---|
| Schema, field, fieldset | `system_name` | Stable across environments. It is also the warehouse table and column name, so it must not change casually. |
| Dropdown | registry key + `name` | V3 dropdowns have no system name |
| Dropdown option | `name` within its dropdown | |
| Registry | key in `environments/<env>.yaml` | Maps to the registry name in each tenant |

- Object IDs differ per tenant. `ids/<env>.json` maps keys to IDs, and export regenerates it.
- State files never contain IDs, which is what lets one set of files describe several environments.

### Defaults and noise

- State files hold only settings someone chose. Values equal to Benchling defaults are omitted on export.
- Read-only and volatile values are never written:
  - timestamps
  - creators
  - IDs
  - counts
  - computed fields
- Export output is deterministic: sorted keys, stable field order, fixed formatting. Exporting an
  unchanged tenant twice must produce no diff.

## Operations

### export

- Reads a tenant through a read-only client and writes `config/` and `ids/<env>.json`.
- Bootstraps a new config repo from an existing tenant.
- Repeatable at any time. A non-empty `git diff` after export means the tenant changed outside git.

### plan

- Loads `config/`, reads the live tenant, and produces an ordered list of operations.
- Writes a plan file (JSON plus a readable summary) whose name includes its content hash.

| Operation class | Examples | Default |
|---|---|---|
| Additive | create schema, add field, add dropdown option, add validation rule | Allowed |
| Modifying | rename display name, change prefix, make a field required, change naming template | Allowed |
| Destructive | archive a field, schema or option; change a field's type; remove a fieldset | Blocked unless `--allow-destructive` |
| Manual | anything the API can't write | Listed with instructions; never executed |

- **Ordering:**
  1. units
  2. dropdowns and options
  3. fieldsets
  4. schemas, then their fields
  5. validation rules
  6. naming templates, which refer to fields
- **Renames:** a diff can't tell a rename from an archive plus a create.
  - A system-name change must be declared with `renamed_from: <old_system_name>` in the state file.
  - Without the hint, plan reports an archive and a create. Archiving is destructive, so the
    plan is then blocked.
- **Drift:** running plan against an environment with no pending changes in git produces
  operations only for changes made by hand. CI runs this on a schedule and reports drift.

### apply

- Takes a plan file, re-plans against the live tenant, and refuses to run if the hash differs.
  That means the tenant changed after review.
- Executes operations in order.
- `set_field_definitions` replaces a schema's full field list and runs as an async task, so apply
  sends the complete list and polls the task.
- Stops at the first failure and reports what ran. It does not roll back, and re-running plan
  shows what remains.

### promote

- Applies the same `config/` to the next environment.
- There is no separate promotion step: a release tag triggers plan and apply against test, then prod.
- Benchling's native configuration migration has no API (only a read-only import history), so
  this design cannot drive it.

## API coverage

Checked against `benchling-v3-sdk-python` 15.0.0. Most of these endpoints are beta and need the
`EARLY-ACCESS: true` header.

| Configuration | Read | Write | v1 scope |
|---|---|---|---|
| Entity schemas (all typed families) | ✓ | create, update, set fields, apply/remove fieldset | ✓ |
| Naming templates, prefixes, naming options, constraints | ✓ | via schema update | ✓ |
| Validation rules | ✓ | create, update | ✓ |
| Fieldsets | ✓ (field list empty in practice) | create, update, set fields, delete field | ✓ |
| Result schemas | ✓ | create, update, set fields | ✓ |
| Entry schemas | ✓ | create, update, set fields | ✓ |
| Container, box, plate, location schemas | ✓ | create, update (no field writes) | ✓ (properties only) |
| Dropdowns and options | ✓ | create, update (options via dropdown update) | ✓ |
| Units | ✓ | create, update | ✓ |
| Projects, folders, teams | ✓ | create, update | later |
| Policies, collaborations | ✓ | update, add/remove statements, create/delete | later, needs its own review |
| Run schemas | ✓ | ✗ | manual |
| Entry templates, template collections | ✓ | ✗ | manual |
| Registries | ✓ | ✗ | manual |
| Review processes | ✓ | ✗ | manual |
| Apps and app config | ✓ (config values unreadable) | ✗ | out of scope |
| Warehouse custom views | ✓ | ✗ | manual |

A known read gap affects export. The API returns an empty field list for fieldsets, so export
can't yet tell fieldset fields from fields defined on the schema. Phase 1 must resolve this
(for example, from field `derivationType` or by asking Benchling) before fieldsets are
round-tripped.

## Safety

- **Credentials:**
  - Each environment has its own Benchling App with admin rights to configuration, and nothing
    more than apply needs.
  - Secrets live only in the config repo's CI secrets, never on laptops or in state files.
  - Export and plan use a separate read-only app.
- **Read-only by default:**
  - The library's apply refuses read-only clients.
  - The CLI builds a write client only for `apply`.
- **Reviewed plans only:** apply runs the plan someone approved, checked by hash.
- **Destructive changes are opt-in** per run, and listed separately in the plan summary.
- **Environment gates:**
  - Pull requests plan against dev.
  - Merging to `main` applies to dev.
  - A release tag plans and applies to test, then prod, with a manual approval step for prod.
- **Audit:** every write appears in Benchling's audit log under the app's identity. The CLI
  adds the git commit SHA to its log output, so a change can be traced from tenant to commit.

## Testing

| Level | What | Where |
|---|---|---|
| Unit | Model validation, YAML round-trip, plan diffing, operation ordering, destructive classification | Fakes; no tenant |
| Round-trip | Export, then plan against the same tenant, must produce an empty plan | Every supported object type, on the sandbox |
| Integration | Apply additive, modifying and destructive plans, then export and compare | A dedicated sandbox tenant, never one holding real data |
| Drift | Make a change in the UI and confirm plan reports it | Sandbox |

The empty round-trip plan is the release gate for each object type. An object type is
supported only when its round-trip is clean.

## Phases

| Phase | Delivers | Writes? | Exit criteria |
|---|---|---|---|
| 1. Export | `config.model`, `config.export`; config repo template | No | Deterministic export of entity, result and entry schemas, dropdowns and units from at least three tenants; re-export produces no diff |
| 2. Plan | `config.plan`; drift report in CI | No | Round-trip plans empty for all phase-1 types; a hand-made UI change shows up |
| 3. Apply (additive) | `config.apply` for create and add operations; the CLI | Yes, sandbox | Additive plans apply on the sandbox and re-plan empty |
| 4. Modify and destroy | Modifying and destructive operations, `renamed_from` | Yes, sandbox | Field type change and rename scenarios pass on the sandbox |
| 5. Promote | CI templates for dev → test → prod | Yes | One change set promoted across three environments |

Phases 1 and 2 carry no write risk and are useful on their own.

## Build or adopt

[Liminal ORM](https://github.com/dynotx/liminal-orm) (Apache-2.0, maintained by Dyne
Therapeutics) already does code-first schema management with migrations for entity schemas,
result schemas and dropdowns.

| | Liminal | This design |
|---|---|---|
| Source of truth | Python classes plus Alembic-style revision files | Declarative YAML; plans computed from it |
| Reviewability by non-developers | Lower (Python) | Higher (YAML) |
| Coverage | Entity schemas, result schemas, dropdowns | Phase 1 adds entry and storage schemas, units, fieldsets |
| Dependencies | V2 `benchling-sdk`, SQLAlchemy 1.x, many pins | involve-benchling (V3 SDK only) |
| Credentials | Admin user account | Per-environment admin app |
| Cost | Adopt and learn | Build phases 1–5 |

**Decision point before phase 3:**
1. Run Liminal's `generate-files` and a no-op migration against the sandbox.
2. Adopt Liminal's apply if it round-trips cleanly and the dependencies are acceptable, and
   keep this design's export, plan and drift as the review layer.
3. Otherwise build phase 3.

## Risks

| Risk | Mitigation |
|---|---|
| Beta V3 endpoints change without notice | Pin the SDK; the round-trip suite runs nightly against the sandbox |
| A `set_field_definitions` call drops fields | Apply always sends the full list built from the live tenant plus the plan; a round-trip test covers it |
| People keep editing in the UI, so git drifts | Scheduled drift plans; the team agrees which environments allow UI edits (dev only) |
| Admin credentials leak | CI-only secrets, per-environment apps, rotation runbook |
| System-name changes break warehouse SQL and Insights dashboards | Plan flags any `system_name` change and lists the warehouse tables and columns it renames |
| One schema's partial apply leaves an inconsistent state | Stop on first failure, re-plan to see what remains, never auto-retry destructive operations |

## Open questions

1. Fieldset field lists come back empty. Is that a permission, an API bug, or by design? Ask Benchling.
2. Policies and collaborations are writable. Does access-as-code belong in this tool, or in a
   separate one with its own review?
3. Should state files carry descriptions and tooltips, which are settings, or leave them in the UI?
4. YAML or a typed Python DSL for state files? This doc assumes YAML for reviewability.
